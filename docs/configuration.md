# Configuration

All settings live in one file, `.env`, in the repository's root folder on your server.
`./scripts/setup.sh your.domain` creates it from `.env.example` and fills in the secrets.
Keep it private: it's in `.gitignore` and must never be committed.

After changing `.env`, apply it with:

```bash
docker compose up -d
```

Docker recreates only the containers whose settings changed. Nobody is signed out, except when
`BETTER_AUTH_SECRET` changes.

For local development (without Docker), the same settings go in `server/.env` and
`client/.env.local`: see `server/.env.example` and `client/.env.example`.

## Required

| Setting | |
|---|---|
| `DOMAIN` | Where Kudos Kit runs, without `https://`, e.g. `feedback.example.com`. The dashboard, the API and `kkw.js` are all served here. Links in emails and sign-in redirects use it. |
| `POSTGRES_PASSWORD` | The database owner's password. Generated by `setup.sh`. |
| `DB_INGEST_PASSWORD` | Password of `feedback_ingest`, the role the public feedback endpoint uses. It can only add feedback and read the list of projects. Generated. |
| `DB_ADMIN_PASSWORD` | Password of `feedback_admin`, the role the dashboard uses. It can't change the table structure. Generated. |
| `BETTER_AUTH_SECRET` | Signs login sessions; at least 32 characters (`openssl rand -hex 32`). Generated. **Changing it signs everyone out.** |

The database passwords can be changed at any time: the `migrate` container updates the roles
on the next `docker compose up -d`. Don't change `POSTGRES_PASSWORD` after the first start:
PostgreSQL only reads it when the database is created.

## Home page

| Setting | Default | |
|---|---|---|
| `LANDING_PAGE` | on | Visitors who aren't signed in see a page introducing Kudos Kit at `https://DOMAIN/`. `false` sends them straight to the sign-in page instead, which most installations want. |

## Reverse proxy

| Setting | Default | |
|---|---|---|
| `COMPOSE_PROFILES` | empty | Empty: you use your own nginx (`deploy/nginx/kudoskit.conf`). `caddy`: Docker also starts Caddy, which gets HTTPS certificates by itself. See [DEPLOY.md](../DEPLOY.md). |
| `SERVER_PORT` | `3100` | Port of the API on the server itself (`127.0.0.1` only), for nginx. |
| `CLIENT_PORT` | `3101` | Port of the dashboard on the server itself, for nginx. |

## Spam protection (Cloudflare Turnstile)

Every feedback message passes Cloudflare's [Turnstile](https://www.cloudflare.com/products/turnstile/)
check: free, and usually invisible to people.

| Setting | |
|---|---|
| `TURNSTILE_SITE_KEY` | The public key. The dashboard's Widget page puts it in the install code; every site uses the same one. |
| `TURNSTILE_SECRET` | The secret key the server uses to verify each message. |

To get them: in the [Cloudflare dashboard](https://dash.cloudflare.com/) → **Turnstile** →
**Add widget**. Mode "Managed" is fine. Under **Hostnames**, add your `DOMAIN` and the domain of
every site that will show the widget. Add a new site's domain there before putting the widget
on it.

- One domain covers its subdomains (`myshop.example` allows `www.myshop.example` too).
- The free plan allows 10 hostnames per widget.
- The site key and the secret must come from the **same** Turnstile widget.

**Trying it out first?** Cloudflare's test keys let every message through without a check:

```bash
TURNSTILE_SITE_KEY=1x00000000000000000000AA
TURNSTILE_SECRET=1x0000000000000000000000000000000AA
```

(With `TURNSTILE_SITE_KEY` empty, the Widget page already uses the test site key, but the
server then has no secret and refuses every message.) Replace both with real keys before real
users send feedback.

## Email (Brevo)

Optional. Without it, Kudos Kit still works: invitation and password-reset links are printed
in the server log (`docker compose logs server`) and the dashboard offers "Copy link".

| Setting | |
|---|---|
| `BREVO_API_KEY` | From [Brevo](https://www.brevo.com/) → SMTP & API → API keys. |
| `BREVO_FROM_EMAIL` | The sender address. It must be a sender or domain you've verified in Brevo. |
| `BREVO_TO_EMAIL` | Who gets an email when new feedback arrives (at most one email per minute). Empty: no alerts; invitations and password resets still work. |

## Google and Apple sign-in

Optional. Each provider turns on when all of its settings are filled in. Signing in with
Google or Apple never creates an account: people still need an invitation. Setup steps:
[sign-in-providers.md](sign-in-providers.md).

| Setting | |
|---|---|
| `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` | From a Google Cloud OAuth client. |
| `APPLE_SERVICES_ID`, `APPLE_TEAM_ID`, `APPLE_KEY_ID` | From your Apple Developer account. |
| `APPLE_PRIVATE_KEY_PATH` | The `.p8` key's path **inside the container**: put the file in `./secrets/` on the server and set e.g. `/app/secrets/AuthKey_ABC123DEFG.p8`. The server won't start if the file can't be read. |

## Privacy page

`https://DOMAIN/privacy` explains what the widget collects and how long it's kept. It reads
the facts (retention, email, sign-in providers) from your settings; these fill in who you are:

| Setting | Example |
|---|---|
| `PRIVACY_OPERATOR` | `Example Ltd, 1 Main Street, London` (who runs this installation) |
| `PRIVACY_CONTACT_EMAIL` | `privacy@example.com` |
| `PRIVACY_HOSTING` | `Hetzner Online GmbH, Germany` (where the server is) |
| `PRIVACY_AUTHORITY` | The data protection authority people can complain to, e.g. `ICO (ico.org.uk)` |

| Setting | Default | |
|---|---|---|
| `FEEDBACK_RETENTION_DAYS` | `90` | Feedback older than this is deleted automatically every day. `0` keeps it until someone deletes it. Expired sessions and old invitations are cleaned up too. |

This page helps you be transparent, but it isn't legal advice: check what your own situation
requires.
